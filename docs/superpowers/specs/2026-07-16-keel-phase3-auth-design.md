# Keel Phase 3: Auth (GoTrue) — Design

**Date:** 2026-07-16
**Status:** Approved by Mayur (brainstorming session)
**Scope:** Phase 3 of the Keel platform — self-hosted authentication in the
user's own AWS account, the Supabase-auth replacement.

## Vision fit

Keel is a BYO-AWS platform. Phase 1 (deploy), B1/B2 (AWS runtime), and Phase 2
(managed Postgres) are complete and live-verified. Phase 3 adds **auth** as an
independently selectable resource. With Phase 2's database, this delivers the
core of Supabase — **"Postgres + auth in your own AWS"** — for most apps.
Per D-11, Phase 3 auth is the approved next milestone; per D-8, every resource
Keel provisions is tagged `keel:project=<name>` at creation.

## Decisions made

| Decision | Choice |
|---|---|
| Auth engine | Bundle **GoTrue** (Supabase's own auth server, image `supabase/auth`) — highest fidelity to "replace Supabase", stores users in the app's Phase-2 Postgres, minimal custom auth code |
| Email | **Autoconfirm** now (`GOTRUE_MAILER_AUTOCONFIRM=true`, no SMTP) — signup creates an active user immediately. SMTP/SES confirm+reset flows are a later follow-up |
| Scope | Email+password signup/login + JWT issuance + app integration. **Deferred to later phases:** social OAuth, the PostgREST auto-API + Postgres RLS, MFA, a user-management dashboard, email flows |
| Resource model | Auth is a third independent resource (alongside apps and dbs), referencing a database |

## The resource model

Auth is a Keel resource tracked in the existing DynamoDB registry:

- **Auth record (new):** `PK=AUTH#<name>, SK=META` with attributes: `name`,
  `db` (the linked database name), `project`, `host` (GoTrue's public URL host),
  `port` (the ALB listener port in port mode), `stack` (the CloudFormation
  stack), `taskSgId`, `createdAt`. The **JWT secret is never in DynamoDB** — it
  lives in SSM SecureString `/keel/auth/<name>/jwt-secret`.

It **references a database**: `keel auth create <name> --db <dbname>` requires
an existing `DB#<dbname>` record. GoTrue owns an `auth` schema inside that
Postgres (it creates its own tables on first boot). Apps link to it via an
optional `"auth": "<name>"` field in `keel.json`, symmetric with `"db"`.

## Infrastructure

GoTrue runs as a **Fargate service behind the shared ALB**, from the prebuilt
public image `supabase/auth` — **not** a CodeBuild build. This is the one new
infra path in Phase 3: running a public container image as a Keel-managed
service (no repo, no build step).

**`infra/auth.yaml`** (per-auth CloudFormation stack `keel-auth-<name>`),
mirroring the app stack (`infra/app.yaml`) but simpler:
- Parameters: `AuthName`, `Cluster`, `VpcId`, `Subnets`, `AlbArn`, `AlbSgId`,
  `Mode` (port/domain), `AlbPort`, `Priority`, `BaseDomain`/`HttpsListenerArn`/
  `HostedZoneId` (domain mode), `DbSgId`, `Image` (default `supabase/auth:v2`),
  `Project`.
- Resources:
  - `TaskSg` (own SG, ingress on GoTrue's port `9999` from the ALB SG only).
  - `DbIngress` (conditional on `DbSgId`, `AWS::EC2::SecurityGroupIngress` on
    the DB SG sourced from `TaskSg` on 5432) — the exact #15-fix pattern, so
    GoTrue can reach Postgres before its service must go healthy.
  - `TargetGroup` (target-type `ip`, health check `GET /health`, GoTrue's
    liveness endpoint).
  - `Service` (Fargate, split `ServicePort`/`ServiceDomain` per mode with
    `DependsOn` on the listener/rule, `HealthCheckGracePeriodSeconds: 60`),
    task def container `supabase/auth` with the env below and its secrets
    pulled from SSM (`GOTRUE_DB_DATABASE_URL`, `GOTRUE_JWT_SECRET`).
  - Port mode: a `Listener` on `AlbPort`. Domain mode: a `ListenerRule` +
    Route53 CNAME (`auth-<name>.<baseDomain>` → ALB). Output `Url`.
  - All taggable resources carry `Tags: [{ Key: "keel:project", Value: !Ref Project }]` (D-8).
- Output: `Url` (`http://<alb>:<port>` or `https://auth-<name>.<domain>`),
  `TaskSgId`.

## GoTrue configuration

Environment passed to the container (secrets injected from SSM as task-def
secrets, not plaintext):
- `GOTRUE_DB_DRIVER=postgres`, `GOTRUE_DB_DATABASE_URL=<db url from SSM>` — the
  linked database's connection string (owner role, so GoTrue can create its
  `auth` schema).
- `GOTRUE_JWT_SECRET=<generated, from SSM>` — the signing secret.
- `GOTRUE_JWT_EXP=3600`, `GOTRUE_JWT_AUD=authenticated`.
- `GOTRUE_MAILER_AUTOCONFIRM=true` — no SMTP; signups are immediately active.
- `GOTRUE_DISABLE_SIGNUP=false`, `GOTRUE_SITE_URL=<the auth Url>`,
  `GOTRUE_API_HOST=0.0.0.0`, `PORT=9999`.
- `GOTRUE_EXTERNAL_EMAIL_ENABLED=true`, `GOTRUE_EXTERNAL_PHONE_ENABLED=false`.

The JWT secret is generated by the CLI (`randomBytes(32).toString("hex")`),
stored in SSM `/keel/auth/<name>/jwt-secret` (SecureString), and reused (not
regenerated) on re-deploy.

## Commands

- `keel auth create <name> --db <dbname> [--project <p>]` — validate name
  (`^[a-z][a-z0-9-]{1,31}$`) and that the DB exists; ensure ingress; ensure/read
  the JWT secret; deploy `keel-auth-<name>` (grant its task SG on the DB SG via
  the stack); write the `AUTH#<name>` record; print the GoTrue URL + a note that
  the JWT secret is in SSM. Grants the auth service DB access via the same
  in-stack `DbIngress` mechanism as apps.
- `keel auth list` — `name  db  project  url` per record.
- `keel auth url <name>` — print the GoTrue API URL.
- `keel auth destroy <name> [--yes]` — delete the `keel-auth-<name>` stack
  (removes the service + its DB ingress grant, lifecycle-managed), the SSM JWT
  secret, and the registry record. Leaves the database and its `auth` schema
  intact (destroying auth shouldn't drop user data). Confirmation-gated.

## App integration

`keel.json` gains an optional `"auth": "<name>"` (validated like `db`). On
`keel deploy` (aws target), when `auth` is set:
1. keel reads the auth record and its JWT secret from SSM,
2. injects `GOTRUE_URL` (the GoTrue API URL) and `JWT_SECRET` (the shared
   secret) into the app's env store (SSM `/keel/<app>/env/*`), so the existing
   task-def secret mechanism carries them,
3. no extra network wiring is needed — the app validates JWTs locally with the
   secret; the browser/client calls the public GoTrue URL directly.

## Data flow: an app with a database and auth

```
keel db create appdb                 # Phase 2: Postgres
keel auth create appauth --db appdb  # GoTrue on appdb, public URL printed
# app keel.json: { ..., "db": "appdb", "auth": "appauth" }
keel deploy                          # injects DATABASE_URL + GOTRUE_URL + JWT_SECRET
# client → POST <gotrue>/signup {email,password} → user active (autoconfirm)
# client → POST <gotrue>/token?grant_type=password → { access_token: <JWT> }
# client → app request with Authorization: Bearer <JWT>
# app verifies the JWT with JWT_SECRET; reads user rows from appdb (auth.users)
```

## Security

- JWT secret generated (32-byte), stored only in SSM SecureString, never in
  DynamoDB, never logged, injected into GoTrue and apps as task-def secrets.
- GoTrue's task SG accepts ingress only from the ALB SG; its DB access is the
  in-stack `DbIngress` grant (removed automatically on `keel auth destroy`).
- Autoconfirm means no email verification in the MVP — appropriate for
  internal/dev apps and the owner's own products; documented clearly. SMTP/SES
  verification is a tracked follow-up before this is used for untrusted public
  signups.
- GoTrue is exposed publicly (the client must reach it) over the ALB. In port
  mode that's HTTP; production use should pair with domain mode (HTTPS) — noted
  in the GUIDE.

## Error handling

- `keel auth create` with a missing `--db` or non-existent database → actionable
  error naming `keel db create`.
- Duplicate auth name → error.
- Control plane / ingress missing → the existing `keel setup` hint.
- GoTrue failing to reach the DB (grant/URL wrong) → surfaced via the deploy
  wait timeout with the CloudFormation/ECS reason; `keel auth destroy` cleans up.
- App links `"auth"` but the auth resource doesn't exist → fail fast before the
  build, naming `keel auth create`.

## Testing

- All AWS access through the injected-client seam; no test hits the network or a
  real GoTrue.
- Unit tests: name validation, `AUTH#` registry round-trip, JWT-secret
  ensure-or-generate, the auth-stack params per mode (incl. `DbSgId` and the
  `keel:project` tag), `keel auth create/list/url/destroy` command wiring, and
  the deploy-time `GOTRUE_URL`/`JWT_SECRET` injection (asserted to land in the
  app env before the build).
- Live verification (with the user): `keel db create` + `keel auth create`, then
  `curl` a `/signup` and a `/token?grant_type=password` against the GoTrue URL to
  get a real JWT, decode/verify it with the SSM secret, then `keel auth destroy`
  — on real AWS, torn down after.

## Out of scope (Phase 3)

Social OAuth providers, the PostgREST auto-generated REST API, Postgres RLS
policy management, MFA, a user-management dashboard, SMTP/email confirm+reset
flows (autoconfirm only), and phone auth. Each is a candidate for a later phase.

## Reuse & new work

- **Reuses:** the DynamoDB registry patterns (Phase 2), the JWT-secret
  ensure-pattern (like `ensureWebhookSecret`), the shared ingress stack (B2), the
  in-stack `DbIngress` grant (#15 fix), and the per-app-SG + service-split CFN
  idiom (B2/#15).
- **New:** `infra/auth.yaml` (a service from a prebuilt image, no CodeBuild),
  `src/aws/authstack.ts`, `src/commands/auth.ts`, `AUTH#` registry functions,
  the `keel.json` `auth` field, and deploy-time auth injection in `deployAws`.
- Resource tagging (`keel:project`) is included on the auth stack now (D-8),
  ahead of the dedicated tagging/registry milestone (D-11), because retro-tagging
  is miserable and tagging at creation is cheap.
